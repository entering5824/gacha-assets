# gacha-assets
Canonical asset metadata and validation-first pipeline for Character Counter, Zenlentering, and GenEntering. Consumers can retain their existing storage.
Pipeline: Discover, Resolve, Download, Validate, Decode, Normalize, Hash, Diff, Publish.
Never publish or mark an asset ready unless bytes are non-empty, Pillow verifies and fully decodes the image, dimensions are within limits, and normalization succeeds. Extensions and MIME types are advisory. A rejected item aborts the batch; manifest replacement is last.
Install this Python package, then use: `gacha-assets run --input discovery.json --manifest manifests/genshin.json --public-root cache`. The command downloads or reads the supplied source bytes, validates and normalizes every image, hashes it, and writes the verified bytes locally. Its manifest is Asset Contract v1. A partial discovery batch merges by `assetId` and preserves assets it did not see; conflicting hashes for a shared storage path abort the batch. The legacy JSON-list manifest is accepted once and upgraded to v1.

Keep shared verified bytes in the git-ignored `cache/` directory using each contract record's relative `path` (for example, `cache/assets/games/...`). Use `--public-root cache` when ingesting and `--assets-root cache` when publishing or syncing a consumer. This keeps the canonical byte source independent from any consumer's runtime bundle; after remote GET/hash/decode coverage reaches 100% and the remote manifest is verified, a web consumer can remove its duplicated local images.
GitHub Trees, Cloudinary Admin API, and explicitly configured Enka JSON catalog adapters are provided. No undocumented Enka endpoint is assumed.

`gacha-assets check-cc-regressions --candidates discovered-objects.json --output reports/character-counter-regressions.json` runs the four historical Character Counter failures against exact `assetId` candidates. The resolver does not synthesize URLs. Each candidate must pass HTTPS HEAD (`image/*`), GET (`image/*`), Pillow decode and normalization; absent candidates are `unresolved` (`no_source_asset` only after a discovered catalog was supplied).

`gacha-assets discover-gen-materials --game-data <GenEntering>/genentering/data/game_data.json --assets-root <GenEntering>/genentering/assets --output reports/genentering-upstream-candidates.json` discovers only missing/invalid local mappings and checks actual upstream icon variants through the documented genshin.dev API. Key/name matching is exact after canonical normalization; it will not turn a guessed icon URL into a candidate. Then run `gacha-assets import-gen-materials --game-data <GenEntering>/genentering/data/game_data.json --assets-root <GenEntering>/genentering/assets --candidates reports/genentering-upstream-candidates.json --manifest manifests/genentering-genshin-materials.json --report reports/genentering-material-import.json`. Unmatched keys are `missing` with `reason: no_source_asset`; ambiguous or invalid candidates are reported as failed and never marked ready.

For current Genshin material names that are absent from genshin.dev, `discover-gen-materials-gdb` batch-matches exact English material names against the GenshinDB catalog and reads the source-declared `filename_icon`. It emits Alioth image candidates, which remain untrusted until `import-gen-materials` successfully GETs and decodes each image. A catalog match alone never marks an asset ready.

For material names not present in those catalogs, `discover-gen-materials-alioth --game-data <GenEntering>/genentering/data/game_data.json --output reports/genentering-alioth-candidates.json` scans Alioth inventory pages and matches normalized display names exactly. It takes the image URL from the matching catalog card and rejects ambiguous names, unsafe hosts, and non-item icon paths; it never derives URLs from material keys. Feed the result to `import-gen-materials` so HEAD/GET, content type, image decode, normalization, and hash validation still gate publication. Unmatched material keys remain `missing`.

## Consumer delivery

`import-contract` bootstraps a canonical v1 manifest from a project's existing contract after rechecking every ready file's digest and image decode. It preserves provenance and can set the target storage. `publish-supabase` uploads only validated manifest records, skips objects whose public GET hash already matches, verifies every new object by GET/hash/decode, and publishes the remote manifest last. It requires a write-authorized service key; a public key cannot bypass Storage RLS. The CLI reads the ignored project `.env` file, while process environment values take precedence. Copy `.env.example` to `.env` and configure a write-authorized `SUPABASE_STORAGE_API_KEY` or `SUPABASE_SERVICE_ROLE_KEY`; do not send the secret through chat. These are explicit stages: ingest writes verified local bytes and a canonical manifest; publication distributes them to Supabase. Product-specific steps then update Zenlentering's remote contract, Character Counter's MongoDB inventory, or GenEntering's offline bundle. A successful local ingest alone does not mean all consumers have synced.

```powershell
gacha-assets import-contract --input <Zenlentering>/public/assets/asset-contract-v1.json --assets-root cache --manifest manifests/zenlentering.json --storage supabase
gacha-assets publish-supabase --manifest manifests/zenlentering.json --assets-root cache --report reports/zenlentering-publish.json
```

GenEntering uses `import-genentering` to merge its required local bundle with the exact-key material manifest; its package sync then copies only the paths the offline app uses. Character Counter reads the per-game canonical manifests while reconciling MongoDB inventory against Supabase objects. Zenlentering loads `manifests/zenlentering.json`, a cross-game view generated from those same four manifests. After remote coverage is verified, the public asset bytes can be removed while the local contract remains as a metadata fallback; the app resolves images from Supabase at runtime. Manifest uploads use a short cache lifetime so consumers receive inventory updates promptly.

For a per-game master view assembled from consumer contracts, use `gacha-assets merge-contracts --input manifests/zenlentering.json --input manifests/genentering.json --game genshin --manifest manifests/genshin.json`. Duplicate `assetId` values must agree on content hash; the resulting record prefers a ready hashed asset and then the storage adapter priority `supabase`, `public`, `bundled`. For a single cross-game consumer manifest, use `gacha-assets merge-manifests --input manifests/genshin.json --input manifests/hsr.json --input manifests/zzz.json --input manifests/wuwa.json --manifest manifests/zenlentering.json`. Shared paths may retain multiple canonical IDs only when their hashes agree. Conflicting identities or hashes abort before replacing the output.

When importing GenEntering, the local logical character manifest is authoritative for entity identity and variants. CamelCase keys are canonicalized (for example `HuTao` to `hu-tao`), and the consumer's `portrait` key maps to the shared `icon` variant; distinct `artwork` records remain separate. Reused image paths retain every logical asset ID while the byte file is staged once.

For a full cross-game release, `scripts/publish-all-games.ps1` runs the publisher gate for `genshin`, `hsr`, `zzz`, and `wuwa`, then publishes their merged `manifests/zenlentering.json` view last. `-Mode dry-run` validates every cache file without network writes; `-Mode verify-only` checks every remote object and all five manifests; `-Mode publish` uploads missing objects and requires every object and manifest to verify before reporting success. It reads the ignored local `.env` through the CLI; `SUPABASE_STORAGE_API_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, or `SUPABASE_SECRET_KEY` may hold the server-side key. Example: `powershell -ExecutionPolicy Bypass -File .\scripts\publish-all-games.ps1 -Mode publish -PythonPath <python-with-Pillow>`. Reports are written per game and for the merged manifest; reruns are safe because matching objects are skipped.
